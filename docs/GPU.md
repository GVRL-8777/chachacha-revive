# 어떤 폰에서는 3D 가 안 나온다 (Mali · 안드로이드 16)

같은 APK 인데 폰에 따라 화면이 다르다. **게임은 멀쩡히 돌지만 3D 만 안 그려지는**
기기가 있다. 원인을 어디까지 좁혔는지 적어 둔다. 아직 못 고쳤다.

## 증상

| | 갤럭시 A82 (Adreno · 안드로이드 14) | 갤럭시 A35 (Mali · 안드로이드 16) |
|---|---|---|
| 설치 · 실행 | 정상 | 정상 |
| 세이브 · 서버 대체 | 정상 | 정상 |
| UI · 2D 그림 | 정상 | 정상 |
| 파티클 (배기 · 폭발) | 정상 | 정상 |
| **차 (3D 메시)** | 파란 아베오 | **검은 실루엣** |
| **주행 중 길** | 정상 | **안 그려짐 (하늘만)** |

A35 에서도 주행은 끝까지 돌고 점수 · 골드 · 기록이 정상으로 저장된다.
**화면에만 안 나온다.**

## 아니었던 것 (실기로 하나씩 배제)

**깊이 버퍼가 아니다.** 처음엔 이것이 범인처럼 보였다. 로그가 이랬다.

```
Creating OpenGL ES 2.0 context (RGB24 888 0/0)
                                         ↑ 깊이 0 · 스텐실 0
```

깊이 버퍼가 없으면 스카이박스가 화면을 덮고 뒷면이 앞면을 가린다 — 증상과
정확히 맞는다. `assets/bin/Data/settings.xml` 에서

```xml
<bool name="32bit_display">True</bool>
<bool name="24bit_depth">True</bool>
```

로 바꾸니 컨텍스트가 `(RGB24 888 24/8)` 로 바뀌었다. **깊이 버퍼가 붙었는데도
화면은 그대로였다.**

(`24bit_depth` 만 켜서는 안 바뀐다. `32bit_display` 를 함께 켜야 Mali 가
깊이 있는 EGL 설정을 내준다. 이 사실 자체는 다른 데서 쓸모가 있을 수 있다.)

**텍스처 형식도 아니다.** 이 폰은 S3TC(DXT)를 아예 모른다.

```
GL_OES_compressed_ETC1_RGB8_texture     ← ETC1 만
GL_KHR_texture_compression_astc_ldr
s3tc / dxt / atc  →  없음
```

그런데 작업 트리에는 DXT1 287장 · DXT5 18장이 들어 있다. 유력해 보였지만
두 가지가 이 가설을 깬다.

- UI 아틀라스 `Atlas_MainMenu` · `Atlas_CarIcon` 도 **DXT5 인데 멀쩡히 나온다.**
  유니티가 소프트웨어로 풀어 주고 있다는 뜻이다.
- 아베오 텍스처 4장을 **ETC1 으로 바꿔 구워 봐도 여전히 검다.**
  (DXT1 과 ETC1 은 둘 다 4bpp 라 제자리에서 길이 보존하며 바꿀 수 있다 —
  `_scratch/toetc.py` 방식)

**번들도 아니다.** 복원 번들은 정상으로 열린다.

```
[CNBUNDLE] error=            (비어 있음 = 오류 없음)
[CNBUNDLE] bundle=pack (UnityEngine.AssetBundle)
[CNBUNDLE] mainAsset=Gbeach01 (UnityEngine.GameObject)
```

## 남은 용의자

차 재질이 쓰는 셰이더를 찾아보면 이렇다.

```
재질 AVEO_A · AVEO_B · AVEO_S · AVEO_R_LOW …
   -> Normal-DiffuseFast   (unity default resources)
```

`Normal-DiffuseFast` 는 **조명을 받는** 셰이더다. 반면 멀쩡히 나오는 것들은
전부 unlit 이다 — NGUI 의 `Unlit - Transparent Colored` 무리, 파티클, 폰트.

> **조명을 받는 셰이더만 검게 나온다.**

유니티는 셰이더 컴파일 오류를 하나도 안 뱉는다(릴리스 빌드라 로그를 안 남긴다).
그래서 컴파일이 실패해 검은 대체 셰이더로 떨어지는 것인지, 컴파일은 되는데
조명 값이 0으로 들어오는 것인지 아직 못 가렸다.

곁다리로 이런 경고도 있다. 고칠 수 있는 층이 아니다.

```
linker: "libunity.so" has text relocations and will not work
```

2014년에 구운 32비트 `libunity.so` 는 텍스트 재배치를 쓴다. 안드로이드는
API 23 이상을 겨냥한 앱에는 이것을 막지만, 이 앱은 API 10 을 겨냥해서
경고만 내고 통과한다. 안드로이드 16 에서 이 경로가 온전한지는 알 수 없다.

## 해 볼 만한 다음 수

1. **재질의 셰이더를 unlit 으로 바꿔 본다.** 아베오 재질 하나만 골라
   `Unlit-Normal` 계열로 PPtr 을 갈아 끼우고 굽는다. 색이 돌아오면
   "조명 셰이더가 죽는다" 가 확정되고, 차 · 길 재질을 전부 unlit 으로
   돌리는 것이 우회로가 된다. 대신 음영이 사라져 밋밋해진다.
2. **개발 빌드로 구워 셰이더 로그를 본다.** 유니티 4 는 릴리스에서
   셰이더 오류를 안 찍는다. 로그가 나오면 단번에 끝난다.
3. **Mali 기기를 하나 더 본다.** 안드로이드 16 탓인지 Mali 탓인지 아직 못 가렸다.
   구형 Mali 폰(안드로이드 10 안팎)에서 되면 OS 문제로 좁혀진다.

## 지금 배포본은 어떻게 두었나

`settings.xml` 은 **원래 값(둘 다 False)으로 되돌려 두었다.** 깊이 버퍼를 켜도
A35 에서 달라지는 것이 없었고, A82 에서 검증한 상태를 흔들 이유가 없다.

아베오 텍스처 4장은 ETC1 으로 바뀐 채로 두었다. ETC1 은 모든 GLES2 기기가
아는 형식이고 크기도 같아서 손해가 없다.

## 2차 조사 — 실험으로 좁힌 것 (2026-08-23)

셰이더를 직접 갈아 끼울 수 있게 되면서 훨씬 정밀하게 볼 수 있었다.
`Mobile-Lightmap-Unlit` 을 손으로 쓴 GLSL 프로그램 셰이더로 바꿔 놓고
출력을 바꿔 가며 확인했다.

| 시험 | 결과 | 뜻 |
|---|---|---|
| 빨강만 출력 | 차가 **빨갛게** 나옴 | 메시 · 셰이더 · 그리기 전부 정상 |
| UV 를 색으로 | 제대로 된 **그라데이션** | UV 속성도 정상 |
| `texture2D(_MainTex, uv)` | **검정** | 텍스처만 안 닿는다 |

그래서 남은 것은 **텍스처가 셰이더에 안 묶인다** 하나다.

### 아니었던 것 (모두 실기 확인)

- **텍스처 형식이 아니다.** DXT1 → ETC1 → RGB24(압축 없음) 세 가지로
  구워 봤다. 압축 텍스처 349장을 전부 압축 없이 바꾸고(트리 +140MB)
  구웠는데도 **차 몸통은 그대로 검었다.**
- **샘플러 설정이 아니다.** 차 텍스처는 `Point + Repeat + aniso 0` 이고
  잘 나오는 UI 는 `Bilinear/Trilinear + Clamp + aniso 1~4` 였다.
  (`aniso 0` 은 정상 값이 아니다.) UI 와 똑같이 맞춰도 그대로였다.
- **재질 참조가 끊긴 것도 아니다.** `AVEO` 재질 11개가 모두 알맞은
  텍스처 파일을 가리키고 있다.

### 눈에 띄는 갈림

압축 없이 바꿨을 때 **바퀴 림은 제대로 나왔다.** 같은 차인데 바퀴는
나오고 몸통은 안 나온다. 즉 **재질 단위로** 갈린다. 몸통이 쓰는 재질을
아직 못 짚었다 — 프리팹의 렌더러를 따라가다 다른 차(`SSANENG_R`)의
재질을 짚는 등 헛짚었다.

### 다음에 할 일

1. **차 프리팹의 렌더러 → 재질 → 텍스처를 정확히 따라가기.**
   `m_Component` 구조를 제대로 읽어야 한다. 몸통 재질을 짚으면
   그 텍스처만 보면 된다.
2. **두 폰을 같은 빌드로 나란히 보기.** A82(Adreno)에서 몸통이 정말
   나오는지 같은 APK 로 다시 확인해야 한다. 지금 비교는 서로 다른
   시점의 빌드다.

### 이때 만든 도구

| 도구 | 하는 일 |
|---|---|
| `tools/progshader.py` | 고정기능 셰이더를 손으로 쓴 GLSL 프로그램 셰이더로 교체(`--solid red/uv` 시험 모드) |
| `tools/setshader.py` | 재질이 가리키는 셰이더를 바꾼다 |
| `tools/texsettings.py` | 텍스처의 필터 · 랩 · 이방성을 고친다 |
| `tools/uncompress.py` | 압축 텍스처를 압축 없는 형식으로 (`--survey` 로 비용 확인) |
| `tools/sfedit.py` | 직렬화 파일의 오브젝트를 **길이가 달라져도** 갈아 끼운다 |

`sfedit` 은 이 조사에서 가장 쓸모 있었다. 오브젝트를 파일 끝으로 옮기고
오브젝트 표의 start/size 와 머리의 file_size 만 고치면 된다. 다만
**머리는 큰끝, 메타데이터는 파일이 정한 순서**라 섞으면 파일이 깨진다.

### 3차 — 더 배제한 것

- **몸통 재질은 `SSANENG_R` 이 아니다.** 프리팹의 AVEO 렌더러가 그 재질을
  가리키길래(`m_Component` 는 `(클래스ID, PPtr)` 짝이다 — 137 이
  SkinnedMeshRenderer), 그 텍스처 자리에 **밝은 파란 그림을 강제로 넣어**
  구웠다. 몸통은 그대로 검었다.
- **표본이 어두운 것이 아니라 정확히 0 이다.** 샘플값을 32배로 키워 봐도
  몸통은 순수 검정이었다. 같은 화면에서 다른 부분은 하얗게 포화됐다.
- **파일 누락이 아니다.** 재질 · 텍스처 · 프리팹 파일이 전부 APK 안에 있다.
- **`ChangePlayerModel` 절단 때문도 아니다.** `dbhook.cs` 가 이 메서드를
  `Ret` 으로 자르긴 하지만, 그 패처는 **빌드 사슬에 없다.**
  `scripts/builddll.sh` 는 tunnelfix → notutorial → rankfix → invitefix →
  shopfix → modesfix → tradefix → titlefix 순으로만 돈다.

### 지금 막혀 있는 곳

**A82(Adreno)와 같은 빌드로 나란히 못 봤다.** 윈도가 삼성 ADB 기기를 하나만
본다. 지금의 "A82 는 파랗고 A35 는 검다" 는 **서로 다른 시점의 빌드**를 견준
것이라 근거가 약하다. 같은 APK 로 A82 에서도 검게 나온다면 기기 문제가 아니라
**데이터 문제**이고, 방향이 완전히 달라진다.

## 4차 — 같은 APK 로 두 폰을 나란히 보다 (2026-08-24)

3차에서 막혔던 것을 풀었다. 두 폰을 **동시에 연결**하고 **해시가 같은 APK**를
양쪽에 깔았다. 이제 비교는 근거가 있다.

```
바탕화면 APK      4d1f6aae75ff8a17a8897ea018610c51f67d6579c3a4b327adaf81798800588e
A35 에 깔린 것    4d1f6aae75ff8a17a8897ea018610c51f67d6579c3a4b327adaf81798800588e
```

| | A82 · SM-A826S (Adreno 640 · 안드14) | A35 · SM-A356N (Mali-G68 · 안드16) |
|---|---|---|
| 차 몸통 | 파란 아베오, 텍스처 정상 | 새까만 실루엣 |
| 바퀴 림 | 정상 | **정상 (은색 무늬가 보인다)** |
| UI · 순위표 · 무대 조명 | 정상 | 정상 |

**기기 차이가 확정됐다.** 그리고 같은 차 안에서 갈린다는 것도 확인했다.

## 셰이더로 안을 들여다본 결과

`Mobile-Lightmap-Unlit` 을 손으로 쓴 GLSL 로 갈아 끼우고 출력만 바꿔 가며 봤다.
(`tools/progshader.py --solid ...`)

| 모드 | 프래그먼트 출력 | A35 에서 몸통 |
|---|---|---|
| `red` | `vec4(1,0,0,1)` | **빨강** — 메시도 그리기도 정상 |
| `uv` | `vec4(u, v, 0, 1)` | u≈0.72 · v≈0.05 — **메시 데이터와 정확히 일치** |
| `center` | `texture2D(_MainTex, vec2(0.5,0.5))` | **회청색** — 상수 좌표면 표본이 나온다 |
| `mix` | `vec4(tex.rg, u*0.6, 1)` | **순수 파랑** — UV 는 살아 있고 표본만 0 |

`mix` 화면에서 **바퀴 림은 노랗게** 나온다. 같은 그리기 · 같은 셰이더인데
몸통만 표본이 0 이다. 즉 **재질(텍스처) 단위로** 갈린다.

## 이번에 배제한 것 (전부 실기 확인, 깊이 설정을 켠 상태에서)

- **텍스처 형식이 아니다.** 차 텍스처를 DXT1 → RGB24 → ETC1 → RGB565 로
  바꿔 가며 구웠다. **넷 다 A35 에서 검다.** A82 는 넷 다 정상으로 그린다.
  (참고: A82 의 Adreno 640 에도 S3TC 확장이 없다. 유니티 4 가 DXT 를
  소프트웨어로 푸는 것이다. 그래서 형식은 애초에 갈림길이 아니었다.)
- **메시 압축이 아니다.** 차 고해상도 메시 28개가 `m_MeshCompression=3`
  이라 유력해 보였다. `tools/meshuncompress.py` 를 만들어 전부 풀었는데
  (트리 +1.2MB) 그대로 검었다. 푼 결과는 저장된 AABB 와 양자화 오차 안에서
  일치하고, UV 도 같은 차의 압축 없는 `_LOW` 메시와 첫 값들이 맞는다.
- **정점 스트림 배치가 아니다.** 차는 스트림0=좌표 · 스트림1=UV 로 나뉘고
  맵은 한 스트림에 끼워넣기다. 차 메시를 맵과 같은 배치(20B 끼워넣기)로
  다시 짜도 그대로였다.
- **렌더러 종류가 아니다.** 차 몸통은 전부 `SkinnedMeshRenderer` 인데,
  압축 없는 메시를 쓰는 Phoenix 도 `SkinnedMeshRenderer` 다.
- **라이트맵이 아니다.** 차 렌더러는 전부 `m_LightmapIndex=255`(없음)라
  셰이더의 첫 패스(`LIGHTMODE=Vertex`, `_MainTex` 그대로)를 탄다.
- **샘플러 설정이 아니다.** `aniso 0 → 1`, `Point → Bilinear`,
  `Repeat → Clamp` 를 깊이 설정을 켠 상태에서 다시 시험했다. 그대로였다.
- **NPOT 이 아니다.** 게임 텍스처는 전부 2의 거듭제곱이다.
  NPOT+Repeat 조합은 유니티 기본 리소스에만 있다.
- **재질 참조가 끊긴 것도 아니다.** 트리의 재질 447개 중 405개가
  `_MainTex` 를 제대로 물고 있고, 차고가 쓰는 `AVEO_S` 도 정상이다.
- **번들 문제가 아니다.** `pack.dat` 에는 프리팹만 있고 Texture2D 는 0개다.

## 새로 찾은 **두 번째** 버그 — 깊이 버퍼가 사라진다

로그를 처음부터 받아 보니 컨텍스트가 **두 번** 만들어진다.

```
Creating OpenGL ES 2.0 context (RGB24 888 24/8)   ← 첫 번째: 깊이 있음
Creating OpenGL ES 2.0 context (RGB24 888 0/0)    ← 1~2초 뒤: 깊이 없음
```

같은 APK 로 A82 는 이렇다.

```
Creating OpenGL ES 2.0 context (RGB24 888 16/0)
Creating OpenGL ES 2.0 context (RGB16 565 16/0)   ← 물러나도 깊이는 지킨다
```

앱 실행 전환이 끝나면서 창이 잠깐 사라졌다 나타나고(`onWindowVisibilityChanged(8)`
→ `surfaceDestroyed` → `surfaceCreated`), 그때 유니티가 컨텍스트를 다시 만든다.
**A35 는 그 두 번째에서 깊이 0 인 설정을 잡는다.**

`settings.xml` 조합을 전부 시험했다.

| 32bit_display | 24bit_depth | 결과 |
|---|---|---|
| False | False (원본) | 컨텍스트 1개 · `888 0/0` |
| False | True | 컨텍스트 1개 · `888 0/0` |
| True | False | `888 24/8` → `888 0/0` |
| True | True | `888 24/8` → `888 0/0` |

`default_aa` 2·4, `gles_mode` 1, `hide_status_bar` False 도 전부 무의미했다.
**두 번째 생성은 `settings.xml` 을 아예 안 본다.**

컨텍스트를 만드는 코드는 `libunity.so` 가 아니라 **`classes.dex`(자바)** 에 있다
(`Creating OpenGL ES `·`context (` 문자열이 dex 안에 있고 so 에는 없다).
그래서 고치려면 dex 를 뜯어야 한다.

## 설명 못 한 것 하나

DXT → RGB24 로 바꾼 빌드가 **딱 한 번** A35 에서 완벽하게 나왔다
(`_scratch/cmp/a35_nodxt.png`, 2340×1080 이라 A35 가 맞다). 같은 트리 · 같은
설정으로 그 뒤 7번 더 띄웠는데 전부 검었고, 매번 두 번째 컨텍스트가 `0/0` 이었다.
재현이 안 된다.

## 다음에 할 일

1. **`classes.dex` 의 EGL 설정 고르는 자리를 찾아 깊이를 강제한다.**
   `baksmali`/`apktool` 같은 dex 역어셈블러가 필요하다. EGL 속성 배열은
   `fill-array-data` 로 들어 있지 않아서(0x3025 상수를 찾아봤지만 상수표뿐)
   눈으로 읽어야 한다.
2. **GPU 캡처로 드로우콜을 직접 본다.** Android GPU Inspector 나
   `GL_KHR_debug` 로 몸통 드로우콜의 텍스처 바인딩 상태를 확인한다.
   "표본이 0" 의 진짜 이유는 이걸로만 확실히 갈린다.
3. **Mali 폰을 하나 더 본다.** 안드로이드 16 탓인지 Mali 탓인지 아직 못 갈랐다.

## 5차 — **원인은 하나였다: 깊이 버퍼** (2026-08-24)

4차까지의 결론 중 상당수가 틀렸다. 바로잡는다.

### 결정적 시험

셰이더를 이렇게 고쳐 넣었다.

```glsl
if (dot(texture2D(_MainTex, xlv_TEXCOORD0).xyz, vec3(1.0)) < 0.02) discard;
gl_FragData[0] = texture2D(_MainTex, xlv_TEXCOORD0);
```

표본이 0 인 픽셀만 버린 것이다. 그랬더니 **파란 아베오가 그대로 드러났다**
(`_scratch/cmp/discard_car.png`). 차도 텍스처도 처음부터 멀쩡했다.

### 무엇이 덮고 있었나

차 프리팹 계층에 `Bone_shadow` 가 있다. 이 게임은 **차 메시를 한 벌 더
복사해 납작하게 눌러 그림자로 그린다.** 깊이 버퍼가 없으면 그 복사본이
차 위에 그려진다.

이걸 알고 나면 3·4차의 관찰이 전부 한 줄로 설명된다.

| 그때 본 것 | 실제 |
|---|---|
| "몸통 UV 가 메시와 일치" | **그림자 복사본의 UV** — 같은 메시라 당연히 같다 |
| "몸통 표본이 정확히 0" | 그림자 재질의 텍스처가 검다 |
| "빨강 강제하면 차 모양" | 같은 메시니까 |
| "바퀴 림만 나온다" | 그림자보다 **나중에** 그려진다 |
| "상수 좌표면 표본이 나온다" | 그림자 텍스처의 그 한 점이 검지 않았을 뿐 |

### 그래서 헛수고였던 것들

텍스처 형식(DXT1·ETC1·RGB565·RGB24·밉맵), 메시 압축 풀기, 정점 스트림
배치, 샘플러 설정, NPOT — **전부 이 문제와 무관했다.** 도구는 남았지만
(`tools/meshuncompress.py`, `uncompress.py --small/--etc`) 이 버그에는
쓸 데가 없다.

"DXT→RGB24 로 바꾼 빌드가 한 번 성공했다"는 것도 이제 설명된다.
**그 실행에서 깊이가 살아남았을 뿐이다.** 같은 트리로 10번 더 띄웠을 때
전부 검었고 매번 두 번째 컨텍스트가 `0/0` 이었다.

### 남은 문제 하나

```
A35 :  (RGB24 888 24/8)  →  (RGB24 888 0/0)
A82 :  (RGB24 888 16/0)  →  (RGB16 565 16/0)
```

앱 실행 전환이 끝나며 표면이 다시 만들어지고, 그때 A35 만 깊이 없는 EGL
설정을 잡는다. `settings.xml` 로는 못 막는다 (조합 4가지 · `default_aa`
2·4 · `gles_mode` 1 · 상태바 숨김 해제 전부 무의미).

설정을 고르는 코드는 **`classes.dex`(자바)** 에 있다.

```
"Creating OpenGL ES " 문자열 번호 1930, const-string 자리 1곳 (오프셋 1700242)
EGL 속성 상수 무리 :
  1698114~1698296  설정을 거르는 곳 (EGL_DEPTH_SIZE 를 읽어 16과 비교)
  1715846~1715930  로그 문자열 만드는 곳 ("RGB… …/…")
```

`_scratch/dexfind.py` 로 자리를 찾았고 `_scratch/dexdis.py` 로 대충 읽었지만,
명령 길이표가 부정확해 흐름이 어긋난다. **제대로 된 dex 역어셈블러
(baksmali · apktool)가 필요하다.**

### 다음 수

1. dex 역어셈블러로 EGL 설정 고르는 메서드를 읽고, 깊이 없는 설정으로
   물러나지 못하게 막는다. 이것이 정공법이다.
2. 안 되면 우회로: 그림자 복사본이 **차보다 먼저** 그려지게 만든다.
   깊이가 없어도 순서만 맞으면 차고는 제대로 보인다. 다만 주행 중
   앞뒤 정렬은 여전히 틀린다.

## 6차 — **고쳤다** (2026-08-24)

`baksmali` 로 `classes.dex` 를 풀어 유니티의 EGL 설정 고르는 코드를 읽었다.
`com/unity3d/player/aa.smali` 다. 버그가 그대로 보인다.

```smali
:array_32                    # GLES2 용 조건 배열
.array-data 4
    0x3024  0x4              # EGL_RED_SIZE     >= 4
    0x3023  0x4              # EGL_GREEN_SIZE   >= 4
    0x3022  0x4              # EGL_BLUE_SIZE    >= 4
    0x3040  0x4              # EGL_RENDERABLE_TYPE = GLES2
    0x3033  0x4              # EGL_SURFACE_TYPE = WINDOW
    0x3038                   # EGL_NONE
.end array-data
```

**`EGL_DEPTH_SIZE` 가 없다.** 그래서 `eglChooseConfig` 가 깊이 0 인 설정까지
전부 후보로 돌려준다. 유니티는 그 후보들을 손으로 거르는데(깊이 · 스텐실 ·
색 비트 정확히 일치 · MSAA), 다 걸러지면 조건을 하나씩 풀어 다시 거르고,
그래도 없으면 마지막에 이렇게 한다.

```smali
:cond_96
    if-nez v0, :cond_a0
    new-instance v0, Lcom/unity3d/player/z;
    const/4 v1, 0x0
    aget-object v1, v3, v1          # ← 후보[0] 을 그냥 집는다
```

Mali 에서는 그 **후보[0] 이 깊이 0 짜리**였다. Adreno 는 우연히 깊이 있는
설정이 앞에 와서 멀쩡했다. 기기 차이의 정체가 이것이다.

### 고친 방법

조건 배열 두 개(GLES1용 · GLES2용)에 **`EGL_DEPTH_SIZE 16`** 을 넣고 배열
길이 상수를 11 → 13 으로 늘렸다. 그러면 깊이 없는 설정이 **후보에 아예
안 들어온다.** 마지막 수단으로 후보[0] 을 집어도 깊이가 있다.

`tools/dexegl.py` 가 이 일을 한다.

```
python tools/dexegl.py --check     지금 상태
python tools/dexegl.py             고친다
python tools/dexegl.py --restore   backup/dex 에서 되돌린다
```

smali · baksmali 2.5.2 와 의존성은 `tools/jars/` 에 둔다(메이븐 `org/smali`).

### 결과 — 같은 APK 로 두 기기 모두 정상

```
고치기 전  A35 :  (RGB24 888 24/8)  →  (RGB24 888 0/0)    차가 검정
고친 뒤    A35 :  (RGB24 888 24/8)  →  (RGB24 888 24/8)   정상
고친 뒤    A82 :  (RGB16 565 16/0)                        정상
```

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| A35 차고 (순수 검정 비율) | 70.6% | **17.5%** |
| A35 주행 | 길이 안 보임 | **정상** (다리 · 교통차 · 이펙트 전부) |
| A82 | 정상 | 정상 |

세 번 연속 띄워도 매번 깊이 24/8 이다. **판을 가를 필요가 없다 — APK 한 벌로
아드레노 · 말리 둘 다 된다.**

### 다 쌓은 뒤 다시 확인 (2026-08-24)

한국어화 · 트로이 · 2배 해상도 아틀라스(512²→1024² · 1024×512→2048×1024) ·
번들 7.3→7.7MB · 새 DLL 을 전부 얹은 빌드로 A35 에서 다시 봤다. **그대로다.**

```
Creating OpenGL ES 2.0 context (RGB24 888 24/8)      ← 깊이 살아 있음
로비 순수 검정 비율 16.4%  (고치기 전 70.6%)
```

로비 · 자동차 샵 · 주행(도시 맵) · 점프 · 일시정지→차고 전부 정상이고,
Unity 로그에 예외가 하나도 없다. **아틀라스를 네 배로 키워도 이 드라이버는
아무 탈이 없다.**

> **A35 는 Unity 로그가 logcat 에 나온다.** A82 에서는 안 나온다
> (`adb logcat -s Unity`). 앞으로 게임 안에서 무슨 일이 나는지 봐야 할 때는
> **A35 로 보는 편이 훨씬 빠르다.** 트로이 주행이 멈췄을 때 IL 을 읽어야 했던
> 것도 A82 에 로그가 없었기 때문이다.
>
> 로그에 늘 뜨는 `The referenced script on this Behaviour is missing!` 73개는
> `sfmerge` 가 맵 조각의 스크립트 참조를 비운 자국이다. 맵에는 스크립트가
> 필요 없으므로 그냥 두면 된다(`keepscript` 를 준 차 자산은 안 뜬다).

### 트리에 남긴 변경

**`x77/classes.dex` 하나뿐이다.** `settings.xml` 은 원본 값(둘 다 False)으로
되돌렸다 — dex 를 고치고 나니 필요 없었다. 텍스처 · 메시 · 셰이더도 전부 원본이다.

### 3~5차에서 헛짚은 것들

텍스처 형식(DXT1 · ETC1 · RGB565 · RGB24 · 밉맵), 메시 압축 풀기, 정점 스트림
배치, 샘플러 설정, NPOT — **전부 이 문제와 무관했다.** 검은 그림자 복사본을
