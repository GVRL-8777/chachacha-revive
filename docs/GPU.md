# 어떤 폰에서는 3D 가 안 나온다 (Mali · 안드로이드 16)

같은 APK 인데 폰에 따라 화면이 다르다. **게임은 멀쩡히 돌지만 3D 만 안 그려지는**
기기가 있다. 원인을 어디까지 좁혔는지 적어 둔다. 아직 못 고쳤다.

## 증상

| | 갤럭시 A82 (Adreno · 안드로이드 14) | 갤럭시 A35 (Mali · 안드로이드 16) |
|---|---|---|
| 설치 · 실행 | 정상 | 정상 |
| 세이브 · 서버 대체 | 정상 | 정상 |
| UI · 2D 그림 | 정상 | 정상 |
| 파티클 (배기 · 폭발) | 정상 | 정상 |
| **차 (3D 메시)** | 파란 아베오 | **검은 실루엣** |
| **주행 중 길** | 정상 | **안 그려짐 (하늘만)** |

A35 에서도 주행은 끝까지 돌고 점수 · 골드 · 기록이 정상으로 저장된다.
**화면에만 안 나온다.**

## 아니었던 것 (실기로 하나씩 배제)

**깊이 버퍼가 아니다.** 처음엔 이것이 범인처럼 보였다. 로그가 이랬다.

```
Creating OpenGL ES 2.0 context (RGB24 888 0/0)
                                         ↑ 깊이 0 · 스텐실 0
```

깊이 버퍼가 없으면 스카이박스가 화면을 덮고 뒷면이 앞면을 가린다 — 증상과
정확히 맞는다. `assets/bin/Data/settings.xml` 에서

```xml
<bool name="32bit_display">True</bool>
<bool name="24bit_depth">True</bool>
```

로 바꾸니 컨텍스트가 `(RGB24 888 24/8)` 로 바뀌었다. **깊이 버퍼가 붙었는데도
화면은 그대로였다.**

(`24bit_depth` 만 켜서는 안 바뀐다. `32bit_display` 를 함께 켜야 Mali 가
깊이 있는 EGL 설정을 내준다. 이 사실 자체는 다른 데서 쓸모가 있을 수 있다.)

**텍스처 형식도 아니다.** 이 폰은 S3TC(DXT)를 아예 모른다.

```
GL_OES_compressed_ETC1_RGB8_texture     ← ETC1 만
GL_KHR_texture_compression_astc_ldr
s3tc / dxt / atc  →  없음
```

그런데 작업 트리에는 DXT1 287장 · DXT5 18장이 들어 있다. 유력해 보였지만
두 가지가 이 가설을 깬다.

- UI 아틀라스 `Atlas_MainMenu` · `Atlas_CarIcon` 도 **DXT5 인데 멀쩡히 나온다.**
  유니티가 소프트웨어로 풀어 주고 있다는 뜻이다.
- 아베오 텍스처 4장을 **ETC1 으로 바꿔 구워 봐도 여전히 검다.**
  (DXT1 과 ETC1 은 둘 다 4bpp 라 제자리에서 길이 보존하며 바꿀 수 있다 —
  `_scratch/toetc.py` 방식)

**번들도 아니다.** 복원 번들은 정상으로 열린다.

```
[CNBUNDLE] error=            (비어 있음 = 오류 없음)
[CNBUNDLE] bundle=pack (UnityEngine.AssetBundle)
[CNBUNDLE] mainAsset=Gbeach01 (UnityEngine.GameObject)
```

## 남은 용의자

차 재질이 쓰는 셰이더를 찾아보면 이렇다.

```
재질 AVEO_A · AVEO_B · AVEO_S · AVEO_R_LOW …
   -> Normal-DiffuseFast   (unity default resources)
```

`Normal-DiffuseFast` 는 **조명을 받는** 셰이더다. 반면 멀쩡히 나오는 것들은
전부 unlit 이다 — NGUI 의 `Unlit - Transparent Colored` 무리, 파티클, 폰트.

> **조명을 받는 셰이더만 검게 나온다.**

유니티는 셰이더 컴파일 오류를 하나도 안 뱉는다(릴리스 빌드라 로그를 안 남긴다).
그래서 컴파일이 실패해 검은 대체 셰이더로 떨어지는 것인지, 컴파일은 되는데
조명 값이 0으로 들어오는 것인지 아직 못 가렸다.

곁다리로 이런 경고도 있다. 고칠 수 있는 층이 아니다.

```
linker: "libunity.so" has text relocations and will not work
```

2014년에 구운 32비트 `libunity.so` 는 텍스트 재배치를 쓴다. 안드로이드는
API 23 이상을 겨냥한 앱에는 이것을 막지만, 이 앱은 API 10 을 겨냥해서
경고만 내고 통과한다. 안드로이드 16 에서 이 경로가 온전한지는 알 수 없다.

## 해 볼 만한 다음 수

1. **재질의 셰이더를 unlit 으로 바꿔 본다.** 아베오 재질 하나만 골라
   `Unlit-Normal` 계열로 PPtr 을 갈아 끼우고 굽는다. 색이 돌아오면
   "조명 셰이더가 죽는다" 가 확정되고, 차 · 길 재질을 전부 unlit 으로
   돌리는 것이 우회로가 된다. 대신 음영이 사라져 밋밋해진다.
2. **개발 빌드로 구워 셰이더 로그를 본다.** 유니티 4 는 릴리스에서
   셰이더 오류를 안 찍는다. 로그가 나오면 단번에 끝난다.
3. **Mali 기기를 하나 더 본다.** 안드로이드 16 탓인지 Mali 탓인지 아직 못 가렸다.
   구형 Mali 폰(안드로이드 10 안팎)에서 되면 OS 문제로 좁혀진다.

## 지금 배포본은 어떻게 두었나

`settings.xml` 은 **원래 값(둘 다 False)으로 되돌려 두었다.** 깊이 버퍼를 켜도
A35 에서 달라지는 것이 없었고, A82 에서 검증한 상태를 흔들 이유가 없다.

아베오 텍스처 4장은 ETC1 으로 바뀐 채로 두었다. ETC1 은 모든 GLES2 기기가
아는 형식이고 크기도 같아서 손해가 없다.

## 2차 조사 — 실험으로 좁힌 것 (2026-08-23)

셰이더를 직접 갈아 끼울 수 있게 되면서 훨씬 정밀하게 볼 수 있었다.
`Mobile-Lightmap-Unlit` 을 손으로 쓴 GLSL 프로그램 셰이더로 바꿔 놓고
출력을 바꿔 가며 확인했다.

| 시험 | 결과 | 뜻 |
|---|---|---|
| 빨강만 출력 | 차가 **빨갛게** 나옴 | 메시 · 셰이더 · 그리기 전부 정상 |
| UV 를 색으로 | 제대로 된 **그라데이션** | UV 속성도 정상 |
| `texture2D(_MainTex, uv)` | **검정** | 텍스처만 안 닿는다 |

그래서 남은 것은 **텍스처가 셰이더에 안 묶인다** 하나다.

### 아니었던 것 (모두 실기 확인)

- **텍스처 형식이 아니다.** DXT1 → ETC1 → RGB24(압축 없음) 세 가지로
  구워 봤다. 압축 텍스처 349장을 전부 압축 없이 바꾸고(트리 +140MB)
  구웠는데도 **차 몸통은 그대로 검었다.**
- **샘플러 설정이 아니다.** 차 텍스처는 `Point + Repeat + aniso 0` 이고
  잘 나오는 UI 는 `Bilinear/Trilinear + Clamp + aniso 1~4` 였다.
  (`aniso 0` 은 정상 값이 아니다.) UI 와 똑같이 맞춰도 그대로였다.
- **재질 참조가 끊긴 것도 아니다.** `AVEO` 재질 11개가 모두 알맞은
  텍스처 파일을 가리키고 있다.

### 눈에 띄는 갈림

압축 없이 바꿨을 때 **바퀴 림은 제대로 나왔다.** 같은 차인데 바퀴는
나오고 몸통은 안 나온다. 즉 **재질 단위로** 갈린다. 몸통이 쓰는 재질을
아직 못 짚었다 — 프리팹의 렌더러를 따라가다 다른 차(`SSANENG_R`)의
재질을 짚는 등 헛짚었다.

### 다음에 할 일

1. **차 프리팹의 렌더러 → 재질 → 텍스처를 정확히 따라가기.**
   `m_Component` 구조를 제대로 읽어야 한다. 몸통 재질을 짚으면
   그 텍스처만 보면 된다.
2. **두 폰을 같은 빌드로 나란히 보기.** A82(Adreno)에서 몸통이 정말
   나오는지 같은 APK 로 다시 확인해야 한다. 지금 비교는 서로 다른
   시점의 빌드다.

### 이때 만든 도구

| 도구 | 하는 일 |
|---|---|
| `tools/progshader.py` | 고정기능 셰이더를 손으로 쓴 GLSL 프로그램 셰이더로 교체(`--solid red/uv` 시험 모드) |
| `tools/setshader.py` | 재질이 가리키는 셰이더를 바꾼다 |
| `tools/texsettings.py` | 텍스처의 필터 · 랩 · 이방성을 고친다 |
| `tools/uncompress.py` | 압축 텍스처를 압축 없는 형식으로 (`--survey` 로 비용 확인) |
| `tools/sfedit.py` | 직렬화 파일의 오브젝트를 **길이가 달라져도** 갈아 끼운다 |

`sfedit` 은 이 조사에서 가장 쓸모 있었다. 오브젝트를 파일 끝으로 옮기고
오브젝트 표의 start/size 와 머리의 file_size 만 고치면 된다. 다만
**머리는 큰끝, 메타데이터는 파일이 정한 순서**라 섞으면 파일이 깨진다.

### 3차 — 더 배제한 것

- **몸통 재질은 `SSANENG_R` 이 아니다.** 프리팹의 AVEO 렌더러가 그 재질을
  가리키길래(`m_Component` 는 `(클래스ID, PPtr)` 짝이다 — 137 이
  SkinnedMeshRenderer), 그 텍스처 자리에 **밝은 파란 그림을 강제로 넣어**
  구웠다. 몸통은 그대로 검었다.
- **표본이 어두운 것이 아니라 정확히 0 이다.** 샘플값을 32배로 키워 봐도
  몸통은 순수 검정이었다. 같은 화면에서 다른 부분은 하얗게 포화됐다.
- **파일 누락이 아니다.** 재질 · 텍스처 · 프리팹 파일이 전부 APK 안에 있다.
- **`ChangePlayerModel` 절단 때문도 아니다.** `dbhook.cs` 가 이 메서드를
  `Ret` 으로 자르긴 하지만, 그 패처는 **빌드 사슬에 없다.**
  `scripts/builddll.sh` 는 tunnelfix → notutorial → rankfix → invitefix →
  shopfix → modesfix → tradefix → titlefix 순으로만 돈다.

### 지금 막혀 있는 곳

**A82(Adreno)와 같은 빌드로 나란히 못 봤다.** 윈도가 삼성 ADB 기기를 하나만
본다. 지금의 "A82 는 파랗고 A35 는 검다" 는 **서로 다른 시점의 빌드**를 견준
것이라 근거가 약하다. 같은 APK 로 A82 에서도 검게 나온다면 기기 문제가 아니라
**데이터 문제**이고, 방향이 완전히 달라진다.
